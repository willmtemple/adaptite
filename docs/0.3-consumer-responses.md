# 0.3: adaptite's answers to RUIN and Kiln

The counterpart to `ruin/docs/adaptite-notes.md` and `kiln/docs/adaptite-notes.md`. Those
documents say what the consumers need; this one says what adaptite is doing about each ask,
and — more usefully for the next round — **every place where what shipped differs from what
was requested**, with the reason.

Nothing here is final. 0.3 is unreleased and this is the document to argue with.

**Status:** branch `wtemple/0.3`, open as draft PR #27. Implemented: #7, #15, #17, #18, #19, #20,
#21, #22, #23, #24, #25. Outstanding: #26 (runite 0.3 adoption, blocked on runite publishing).
One bug found on the way and filed rather than fixed: #28.

The contract this all comes with is [`diagnostics.md`](diagnostics.md).

---

## 1. Corrections to the requirements documents

Three load-bearing claims did not survive checking against the tree. Worth reading first,
because two of them change what is actually being asked for.

### 1.1 Kiln #16's headline shipped in 0.2

adaptite#16 leads with "Nothing says which signal caused a render". It was filed 2026-07-29,
one day after 0.2 shipped `DiagnosticEvent::EffectInvalidated`, which carries
`InvalidationCause { node, version, node_origin, write_origin }` **plus** the subscriber effect
and its creation origin — which signal, which subscriber, and the source location of both the
node's creation and the write that moved it, preserved through computed edges.

RUIN has already adopted it (`ruin/docs/performance-profiling.md` documents subscribing under
`RUIN_PROFILE_OUTPUT`). **Kiln's first bug — a pane re-rendering at frame rate because an
unchanged value was written every tick — is answerable from a RUIN profile capture today**,
without any of 0.3.

What was genuinely missing, and what 0.3 adds: invalidation was reported for *effect*
subscribers only, so a `signal → memo → memo → effect` chain reported its two endpoints and
nothing in between; there were no aggregates; and there were no subscriber counts.

### 1.2 RUIN's testing plan is built on a private module

`ruin/docs/plans/testing-and-devtools.md:387-395` proposes a `ReactiveStats` harness that counts
`tracing` events by target, and names its upstream dependency as "an adaptite documentation
change blessing a minimal stable field set on its existing events (targets verified at
`adaptite-0.1.0/src/lib.rs:7-13`)".

`src/lib.rs:6` reads `pub(crate) mod trace_targets`. The targets have never been public API —
the spike read them out of adaptite's source. Worse for that plan, several of the events it
would count are `#[cfg(debug_assertions)]` (`src/reactor.rs:592`, `src/thunk.rs:658`) and do not
exist in the optimized builds RUIN wants to measure.

See §2.4 for the answer. The short version: that harness should be rebuilt on `FlushStats`,
which gives it the same numbers directly and without parsing.

### 1.3 The two most valuable additions were in no requirements document

`ruin/docs/spikes/testing-and-devtools.md:317-320` asks for a public node-dependency enumeration
and a public origin accessor. Both existed as `pub(crate)`. Neither appears in
`ruin/docs/adaptite-notes.md`. They are now public (#19) and were the cheapest items in the
release by a wide margin.

## 2. Declined

Six asks are not being implemented. Each is negotiable — if a case turns up that the
replacement genuinely cannot answer, say so and it gets reopened.

### 2.1 Per-edge dependency add/remove events

*Asked in `adaptite-notes.md`, "P1: computed-work diagnostics", bullet 5.*

Edge recording is `Reactor::try_observe` — the hottest path in the graph, one call per tracked
read. A node with 200 dependencies would emit 200 events per recomputation, and a flush over a
wide graph would emit more diagnostic events than it performs reactive work.

**Instead:** `dependencies_before` / `dependencies_after` on the recompute pair, and
`edges_added` / `edges_removed` per flush.

**Corrected after RUIN's review:** the first version of this said those counts find a read set
that "grows or churns". They do not find churn, and RUIN was right to push back. A computation
that swaps 200 dependencies for 200 different ones reports 200 either side, and the global edge
counters cannot see it either, because every recomputation clears and re-records its whole set —
so churn and stability produce identical totals. What the counts detect is a read set that
changes **size**, which is the shape behind a component that gets slower the longer it lives, and
is covered by a test (`dependency_counts_show_a_computation_whose_read_set_grows`).

For identity churn, sample `dependencies_of` either side of a recomputation or diff two
`debug_graph` snapshots — RUIN's own suggestion, and the right shape, since it is a targeted
investigation rather than something to run per frame. All four documents now say this instead of
the original claim.

**What would still change our mind about per-edge events:** a question about *which* edge that a
targeted `dependencies_of` sample demonstrably cannot answer. It can be added later behind an
explicit opt-in — the events are `#[non_exhaustive]` precisely so that stays additive.

### 2.2 Durations, and any clock

*RUIN already lists this as a non-requirement; Kiln asks for "time taken" in #16.*

Now contractual rather than merely declined. adaptite is `core` + `alloc` over runite; taking a
monotonic timestamp per event would cost more than emitting the event. Every event is ordered
and paired, so a consumer that wants a duration timestamps the pair. This is stated in the
rustdoc for `FlushStats` and `GraphStats` so it stops being re-asked.

### 2.3 Session-scoped peak and cumulative counters

*`adaptite-notes.md` offers: "Peaks and cumulative counts may be scoped to an active diagnostic
session if maintaining them unconditionally has measurable cost."*

Declined in favour of always-maintained, because a peak is `if n > peak` on a line that already
writes `n`, and two modes cost more in documentation and in "are these numbers real right now"
than one mode costs in cycles. Measured, not asserted — see §5.

**But this created a distinction that needs sanctioning** (§4.6): `FlushStats` is *not*
always-maintained.

### 2.4 Stabilising the `tracing` targets and field names

*See §1.2 for why the premise is wrong.*

Blessing log lines as semver-relevant would freeze every internal tracing statement forever, and
could not be honoured for the debug-gated ones at all. The typed diagnostics stream is the
machine-readable contract; `tracing` is for humans reading logs and may change in any release.

**This is a better deal than it sounds.** RUIN's proposed `ReactiveStats` — effect runs, memo
recomputes — now reads straight off `FlushStats` with no parsing, no fragility, and it works in
optimized builds where half the tracing events do not exist.

### 2.5 A feature flag for diagnostics

*Kiln, #16: "Behind a feature flag is fine. None of it needs to be free."*

Generous, but the wrong trade: a `cfg`-gated diagnostic is absent from the binary that has the
problem. 0.2 chose runtime subscription instead — dormant is a boolean check, single-subscriber
delivery does not allocate — and 0.3 keeps that, defended by benchmarks rather than by
assertion.

### 2.6 Node naming and `serde` export

*adaptite#7's own plan.*

Deferred past 0.3, not refused. No consumer asks for it: RUIN correlates on
`(ReactorId, NodeId)` and Kiln never mentions names, while `#[track_caller]` origins already
give the human anchor at zero runtime cost. A `&'static str` per node is steady-state cost on
every node in every application, and `ruin/docs/plans/accessibility.md:192-200` shows RUIN
already declining designs over exactly that kind of cost.

## 4. Delivered differently from the request

This is the section that matters for the next round.

### 4.1 The graph queries did not work as specified (#19)

Every query added takes a `NodeId`, and only `Source` and `EffectHandle` could name their node.
Kiln asks for "subscriber counts **per signal**" — and there was no way to get from a `Signal`
to a node to count. So #19 also adds `Signal::id()`, `Thunk::id()`, `Memo::id()`, `Event::id()`,
and `Reactor::node_version()`, without which the versions returned by `dependencies_of` cannot
be compared against anything and the culprit-finding workflow does not close.

`Reactor::dependency_count()` was added alongside in #22.

### 4.2 `ComputeOutcome` has two variants, not four

The plan listed `Completed | Panicked | Cycle | Disposed`. Shipping: `Completed | Panicked`.

A cycle discovered during a computation *is* a panic — `assert_no_cycle` unwinds with a
`ReactCycleError` message naming the path — and distinguishing it would mean catching and
inspecting the payload on the recompute path for information the panic already carries.
`Disposed` had no reachable path. Shipping enum variants that are never produced is worse than
omitting them; the enum is `#[non_exhaustive]`, so either can be added without a break.

### 4.3 Per-flush totals are one struct, not paired events

*`adaptite-notes.md`: "If Adaptite emits these as paired events rather than a summary type, the
pairing and panic semantics must be documented."*

That requirement is the argument against pairing. A summary emitted at flush close has no
pairing problem to document, survives a panicking job, and costs one struct copy per flush
instead of two events per counted thing. `FlushStats` rides on `FlushFinished`.

### 4.4 Attribution rule for work outside a flush — **please sanity-check this**

Not specified in the request, and there was a real choice.

Work is attributed to **the next flush that closes**, exactly once:

- work during a flush belongs to the innermost flush open at the time, and an inner flush's
  totals are *not* rolled up into the enclosing one, so summing a capture double-counts nothing;
- work outside any flush — most importantly **the writes that scheduled it** — is handed to the
  flush that drains it.

The alternative was attributing pre-flush writes to nothing, which would have made `root_writes`
almost always zero and useless for answering "what set this flush off". A write and the effect
run it causes now land in the same totals. If RUIN's timeline wants the other rule, say so
before this ships — it is cheap to change now and breaking later.

### 4.5 `computed_changed + computed_suppressed` ≤ `computed_recomputed`

Found by the consistency test, not by design. A computation that unwound published nothing and
is therefore neither a change nor a suppression; the difference between the sum and the
recompute count is the number that failed. Documented on the field.

### 4.6 Two classes of counter, with different availability

A distinction the requirements did not anticipate, and the one most worth confirming:

- **`GraphStats` counters are always maintained** — ordinary builds, subscription or not —
  because they back a query that can be called at any moment.
- **`FlushStats` counters are maintained only while a subscription is active**, because they are
  only ever *observed* by being delivered in an event, and an event nobody subscribed to is not
  delivered.

Stated as a rule: *counters that back a query are always maintained; counters that back an event
follow the event.*

**Open:** does RUIN want any `FlushStats` field queryable without a subscription — a
"last flush's totals" accessor, say? That would move those counters into the always-maintained
class and cost accordingly. Nothing in the requirements asks for it, so it is not built.

### 4.7 `NodeKind` is declared at construction, not inferred

A primitive a consumer builds on `source()` reports `Source`, because that is what the graph was
asked to allocate. `Writable` is a memo plus a setter and reports `Memo`. `Resource` and `watch`
compose existing nodes and contribute none of their own. Documented, because the first consumer
to build a custom primitive would otherwise file a bug. This is the same gap that node naming
(§2.6) would close, if it turns out to matter.

### 4.8 Per-kind counts are a method, not an array

`GraphStats::live_nodes_of_kind(NodeKind)` rather than a public `[usize; N]`, so that adding a
`NodeKind` stays additive rather than breaking anyone who sized or destructured by it.

### 4.9 `NodeDisposed` is exactly-once even though `dispose` is idempotent

Disposal is reached from several `Drop` impls and may be called repeatedly; the event fires only
when the node was actually still live. `EffectDisposed` is retained alongside it — that one
reports the effect's own lifecycle transition, this one reports graph bookkeeping being torn
down.

### 4.10 There is no CI performance gate, and there deliberately will not be one

adaptite#25 said "fail CI on regression beyond a stated threshold". Not doing it, because the
numbers say it cannot work: the two real regressions in this release were **9%** and **15.7%**,
both inside the run-to-run variance of a GitHub-hosted runner. A threshold loose enough not to
flake would have caught neither; one tight enough to catch them would flake constantly; and a
perf gate that cries wolf gets disabled, after which it protects nothing.

What ships instead: CI runs every benchmark at low sample counts so they cannot rot, the
saved-baseline A/B is documented as a required human step before changing a hot path, and the
measured numbers are recorded in the contract so drift is visible to a reader.

**This matters to RUIN** because acceptance criterion 6 asks for exactly this gate. If
diagnostics-off cost is important enough to defend automatically, the answer is a dedicated
runner rather than a tighter threshold — say so and it can be built.

### 4.11 `debug_graph` reports no owner tree

adaptite#7's plan lists "nodes, edges, owner tree". `GraphSnapshot` has nodes and edges; the
ownership scope tree is not in it. No consumer asked for it, it lives in a different subsystem
(`src/scope.rs`), and it is the same body of work as #24 — so it moves with #24 rather than being
half-delivered here.

### 4.12 Ownership counters are thread-scoped, not per-reactor

adaptite#24 sat under "graph counters", implying a `GraphStats` field. It cannot be one.
Ownership in adaptite is a thread-local stack — a `scope` has no reactor and never did, and a
frame's parent is whatever was innermost when it was created. Reporting per-reactor would mean
inventing an attribution the implementation does not have, so `ownership_stats()` is a free
function describing the calling thread.

For RUIN this should be a non-event: one reactor per application on one thread makes the two
scopes identical. Flagging it because it is the one number in 0.3 that does not compose if an
application ever runs two reactors on one thread.

`GraphSnapshot` carries an `OwnershipStats` alongside the graph counters, because the two
questions are almost always asked together — a clean graph and an owner tree still holding a
subtree is a leak, and reading them from separate calls invites reading them at separate moments.

### 4.13 The ownership audit is `debug_assert`-shaped, and public

Not requested; worth knowing because RUIN's `TestApp` can use it. Counters that are maintained by
hand drift, so `audit_ownership()` recomputes every live ownership gauge by walking a registry of
live frames, and `debug_assert_ownership_consistent()` fails on disagreement.

The registry is not built when `debug_assertions` is off — making every application pay a `Weak`
push per owner frame to hold a proof nobody reads would be the wrong trade. So the audit is named
and gated exactly like `debug_assert!`: `audit_ownership()` returns `None` in such a build rather
than a misleading empty result, and the assertion compiles to nothing. A test suite that calls it
still builds and runs under `--release`; it simply stops checking.

Where a count *is* the population of a live object, it is not maintained by hand at all — an
`OwnerFrame` holds a tally whose lifetime is the count, so `live_owners` has no call site to
forget. That pattern is worth copying for any counter added later, and it is written up in
`diagnostics.md`.

### 4.14 A breaking change RUIN has to absorb (#17)

Every `DiagnosticEvent` variant is now `#[non_exhaustive]`, not just the enum. Variant patterns
need a trailing `..`. This is mechanical, and it is why every other diagnostics change in 0.3 is
additive rather than breaking. RUIN is the only known subscriber.

## 5. What it costs, measured

RUIN's acceptance criterion 6 is "diagnostics-off benchmarks show negligible regression". These
are real A/B measurements — saved criterion baseline, feature removed, re-run against it — not
estimates. Criterion's *rolling* comparison is too noisy for this and produced a bogus +21.8%
reading during the work that had to be bisected to disprove; use saved baselines.

| Change | Diagnostics-off cost |
|---|---|
| #21 graph counters | Within noise. Two benches no change at p > 0.05; `deep_chain` −0.5%; `layered_diamonds` measured the *uncounted* build 3.9% slower. |
| #22 computed-work | Within noise after the fix. The uncounted build measures 0.7–3.1% *slower* on three of four benches. |
| #23 flush totals | Within noise on the three graph-walking benches (one measures 4.4% faster with the feature); **+3.0%** on the 18 ns `signal_write_read` microbenchmark — one predictable branch guarding depth tracking. |
| `graph_stats()` itself | 7.1 ns over a 1,000-node graph, and flat in graph size by construction. |

**The lesson, learned twice: a guard that exists and does nothing is not free.** #22's first cut
cost ~9% on recompute-heavy benchmarks with diagnostics off, and #23's first cut cost 15.7% on a
bare signal write. Both because a `Drop` type was constructed on a hot path regardless of
whether anyone was listening. Both fixed the same way — the branch goes at the call site, the
guard type lives on the cold side of it. Worth stating for whoever adds the next diagnostic.

## 6a. Answers received from runite (2026-07-29)

- **The ordering guarantee holds.** runite verified the property adaptite batches on —
  *a microtask queued during a turn runs before the next macrotask* — and pinned it with tests;
  their existing coverage did not reach it. A budget that defers a microtask past a macrotask is
  off the table by default, and any future relaxation fails those tests first. adaptite declined
  a pre-emptive opt-out: the hazard is now zero by default, and a second way to queue a microtask
  is permanent cost against a policy that may never land.
- **`current_turn()` is coming, and adaptite will not call it.** runite flagged that a macrotask
  and the microtask it queues get *different* turn ids. Working that through, adaptite needs no
  API change: because diagnostics are delivered synchronously at the moment the work happens, a
  consumer stamps each event with the turn itself, which is finer than anything adaptite could
  bake in. **RUIN should join on the event stream, not on `FlushStats`** — a single `FlushStats`
  can span two turns. Written up in [`diagnostics.md`](diagnostics.md).
  **Corrected 2026-07-30 — see [§6e](#6e-a-correction-to-the-turn-join-advice-2026-07-30).** The
  reasoning above was right; the example attached to it was not. It is a *macrotask* write that
  lands in a different turn from its flush. A write from a spawned task shares a turn with its
  flush.
- **runite 0.3 breaking changes cost adaptite nothing.** `SemaphorePermit`, `next_line`, the
  inherent read/write/seek removals, `unix::Incoming`, `Stdio`/`Command` losing `Clone` — adaptite
  touches none of them. Its entire runite surface is `queue_microtask` and `spawn`.
- **runite#51 (manual clock) does not block adaptite.** Three `resource` tests sequence async work
  by sleeping; the assertions are about ordering but are expressed as wall-clock margins. Not
  flaky today, flaky-in-principle on a loaded runner. Worth having, not worth holding 0.3 for.

## 6b. Answers received from RUIN (2026-07-29), and what changed

Two required items, both done; two corrections, both accepted.

- **#28 promoted to a 0.3 blocker and fixed.** RUIN is right that this is correctness, not
  diagnostic debt. Teardown is now total: every cleanup and child gets an attempt in reverse
  order, each under its own `catch_unwind`; the first panic is preserved and re-raised after
  teardown finishes; and teardown that begins during an existing unwind logs rather than
  re-raises, because re-raising there aborts. Six regression tests in `tests/teardown.rs`,
  including the during-unwind case — which cannot be asserted conventionally, since an abort takes
  the whole suite with it, so reaching the assertions is part of what is being tested.
- **The nested-flush contradiction is resolved, RUIN's way.** Diagnostic flush identity is now
  separate from the divergence epoch, so a re-entrant `flush_now` takes a fresh epoch for
  attribution while staying inside the enclosing logical drain that the guard counts against.
  *One correction to the premise, worth passing back:* the simplest evasion — an effect that
  re-flushes itself — was never reachable, because re-entering a running observer already panics
  with "observer should not already be active". I discovered this by writing a test that passed
  for the wrong reason and checking why. The separation still matters for the indirect case (a
  *second* effect nesting a flush during the same drain resets the first effect's counter) and for
  the contract being self-consistent, which was the actual complaint.
- **`ComputedInvalidated` now carries `state_changed`.** Accepted as asked. Note the aggregate
  counts *deliveries*: `FlushStats::nodes_marked_check`/`nodes_marked_dirty` do not subtract
  coalesced marks, so the event field and the totals answer different questions by design.
- **The dependency-churn claim was overstated and is corrected in all four documents.** See §2.1.

## 6c. Answers received from Kiln (2026-07-29), and one accepted request

Kiln confirmed §4.4 (keep the attribution rule — "cause and effect in one record is precisely what
made the capture possible"), declined §4.6 (no queryable `FlushStats`), accepted §7.5 (counts are
enough for node-versus-value lifetime), and endorsed the `catch_unwind`-per-cleanup shape for #28,
which is what shipped. §7.2, §7.6 and §7.7 drew no Kiln stake. **With RUIN having accepted the
same items, §4.4 and §4.6 are settled and closed.**

Kiln also used the 0.2 stream it had previously reported missing, and attributed its fourth open
performance question to its own code. That is worth knowing here for one reason: it means the
diagnostics are load-bearing in an application, not just in tests.

### Accepted: report suppressed source writes

`Signal::set` compares before writing and returns before touching the graph when the value has not
changed. So a suppressed write produced no `ReactiveWrite`, no flush, and no counter — the only
record was a `tracing` event behind `debug_assertions`, absent from exactly the builds worth
measuring.

Kiln's argument is the one that carries it: a sampler whose signal changed 14 times had *run*
about 80. The equality gate saves the re-render and hides the work, and only the second number
says to slow the sampler down. Two of Kiln's three shipped reactive bugs were that shape.

Shipped as `DiagnosticEvent::WriteSuppressed` (carrying the write's origin, so the discarded work
is attributable to the site that produced it) and `FlushStats::writes_suppressed`. Cost with
diagnostics off is unmeasurable: a suppressed write is 4.33 ns, and the build *without* the
reporting benchmarks 5.1% slower, which is the noise floor.

Kiln also spotted that this generalises — it is the same debug-only-events failure identified in
RUIN's testing plan at §1.2. That prompted an audit of everything adaptite knows only under
`debug_assertions`; it turned up one further case, filed as #29 rather than folded in here.

## 6d. Two changes nobody asked for, both worth knowing about (2026-07-29)

### A semantic decision: re-entrant effect runs are deferred, not rejected

The README documents two things as legal on their own — an effect may write state it
depends on when the loop converges, and `flush_now` exists for hosts that need
synchronous propagation. **Together they re-enter the effect.** The write queues a job
for the effect that is currently running, and the nested flush immediately runs it from
inside the effect's own body, clearing the dependency set the outer run is still
recording.

In 0.2 this was a `debug_assert!`, so release builds fell through into that corruption
and the loop happened to converge. Mid-0.3 I promoted it to an unconditional `assert!`,
which was correct about the hazard and wrong about the remedy: it turned a silently-wrong
release build into a hard panic on a pattern the README sanctions. **That is a production
behaviour change and it is not the one that shipped.**

What shipped instead: a run requested while the effect is already running is *deferred*.
The state mark is left alone, the run is remembered, and it is queued once the current run
finishes. The convergent loop converges as documented and the outer run's dependency set
survives. The `assert!` remains, now guarding only genuinely unreachable re-entry.

**If RUIN or Kiln calls `flush_now` from inside an effect**, this is the change that
affects you, and it should be invisible: the effect's own re-run now happens after the
current run rather than inside it. Anything relying on the re-run completing *before*
`flush_now` returns would see a difference. I do not believe either of you does this, but
it is the one place where "we made it work" and "we changed when it happens" are the same
sentence.

### An unrequested performance change: the graph no longer allocates

Neither of you asked for this; RUIN's report of heavy memory churn in application code
prompted a check of whether adaptite was contributing. It was. A write to the head of a
64-deep memo chain, then reading the tail, cost 383 allocations and 18.8 kB — six per
link, for a graph whose shape never changed. A 64-wide fan-out cost 129.

Both are now zero, and no benchmark regressed (edge re-recording -56.9%, deep-chain
invalidation -43.4%, fan-out -32.1%, node create/dispose -10.7%). Effect runs went from
7 allocations to 2.

Two consequences you may notice:

- `GraphStats::observed_nodes` is now a maintained counter rather than the length of the
  dependents index, because emptied index entries are retained across an observer's rerun.
  **The reported value is unchanged** and is asserted against a walk of the graph in the
  test suite. Named here only because it is the kind of thing that turns into a mystery
  later.
- The graph now *retains* roughly 52-84 bytes per node until disposal instead of churning
  it on every rerun. Steady-state footprint is slightly higher; allocator traffic is
  drastically lower. For a UI that reruns effects every frame this is the right side of the
  trade, but if either of you is measuring resident size rather than allocation rate, it
  is the direction that number moves.

This does not resolve [#37](https://github.com/willmtemple/adaptite/issues/37) — an edge
still *costs* 296 bytes to store 24 bytes of information, because both indexes are nested
hash containers. It stops that cost being paid repeatedly; it does not make it smaller.

## 6e. A correction to the turn-join advice (2026-07-30)

runite 0.3 is published, and `current_turn()` is real, so the advice in
[§6a](#6a-answers-received-from-runite-2026-07-29) could finally be *measured* rather than
argued. One half of it was wrong, and it is the half RUIN would have built on.

**What we told you:** join on the event stream rather than on `FlushStats`, because "the write and
the flush that drains it are in different turns."

**What is actually true**, from `tests/runtime_join.rs`:

| Where the write happens | Write and flush |
| --- | --- |
| A spawned task | **The same turn.** |
| A macrotask | **Different turns.** |
| A synchronous `flush_now` | The same turn as its caller. |

A spawned task is polled *inside* the microtask checkpoint, and the checkpoint drains to
quiescence — so the flush a task's write queues runs before that same turn closes. Only a
macrotask, which runs after the checkpoint has already drained, pushes its flush into the next
turn. runite's original statement to us was about a macrotask and was correct; we generalised it
to "a task" and it does not hold there.

**Why this matters to you rather than being a pedantic fix.** If RUIN writes signals from async
tasks — which is the normal shape for async work driving UI state — then there is no turn boundary
between the write and the flush, and correlation logic written to expect one will either look for a
seam that is not there or silently mis-attribute. The conclusion we gave you is unchanged and still
correct: **stamp events, not aggregates.** It is the reason we gave that was wrong.

**What stops it happening again.** These are properties of runite's scheduling, not adaptite's, so
nothing in adaptite's own test suite would have caught the drift. `tests/runtime_join.rs` now pins
both rows against the real runtime, and it is the test that fails if runite ever changes where the
boundary falls — which is the protection W4 asked for, applied to ourselves rather than to runite.

## 7. Open questions for RUIN and Kiln

Ordered by how much a wrong answer costs to fix later.

1. ~~**The flush attribution rule (§4.4).**~~ **Settled — keep it.** Accepted by both RUIN and
   Kiln; Kiln adds that it does not want per-turn totals, since a turn boundary is a runtime
   detail it has no question phrased in terms of. Original text: Should writes made outside a flush be counted in the
   flush that drains them, as they are now, or attributed to nothing? Cheap to change before
   0.3, breaking after. **Now with more information:** runite has confirmed that the write and
   the flush are in different runtime turns, so the current rule is what keeps cause and effect
   in one record — but it also means a `FlushStats` straddles a turn boundary. If RUIN's timeline
   wants per-turn totals rather than per-flush ones, say so now.
2. **`ComputedInvalidated` volume.** It fires for *every* mark delivered to a computed node,
   including one that coalesces into staleness the node already had, because the event reports
   propagation reaching the node. In a wide graph that is a lot of events. Is that the right
   granularity, or should it fire only on an actual state transition?
3. ~~**Should any `FlushStats` field be queryable without a subscription (§4.6)?**~~
   **Settled — no.** Declined by both: a subscription at mount serves the test case completely.
4. ~~**A teardown bug, found while building #24, filed as #28 rather than fixed.**~~
   **Resolved** — promoted to a blocker at RUIN's request and fixed; see §6b. Original text:
   `OwnerFrame::reset` documents that "a panicking cleanup does not strand its siblings". It
   does: a panic abandons the teardown loop, the remaining cleanups are dropped rather than run,
   and because cleanups run before children are taken, **the owner's children are never disposed
   at all**. This is the teardown path for every effect re-run, so one badly-behaved cleanup in a
   component silently strands everything registered before it and everything it owned — and 0.3's
   new counters will now show that retention without explaining it. Three options are on the
   issue; I lean toward `catch_unwind` per cleanup with the first panic resumed after teardown
   completes. It changes when a panic becomes observable, so it wants a decision, and RUIN's
   hot-reload plan (which leans on `scope_catch`) is the consumer most likely to care.
5. **Node lifetime versus Rust value lifetime.** Found while writing the leak tests, and RUIN's
   leak assertions will meet it: `EffectHandle::dispose()` removes the effect's *node* from the
   graph immediately, but the effect's closure — and anything it captured, including other node
   handles — lives until the last `EffectHandle` clone drops. So a disposed effect can keep a
   memo and its whole input subtree alive, and `live_nodes` will correctly say so. Is a distinct
   signal for "node gone, Rust value still held" wanted, or is the count enough?
6. **Custom primitives report `NodeKind::Source` (§4.7).** Acceptable, or does this revive the
   case for an opt-in label?
7. **Hot-reload and `scope_catch`** — not an adaptite ask, but `ruin/docs/plans/hot-reloading.md`
   fears a `subsecond` unwind propagating through the flush and killing the app, and 0.2's
   `scope_catch` is that boundary. The wrinkle: a caught effect is **disposed**, so "bounded
   retry" means recreating the effect rather than resuming it. Does that make the plan work, or
   is a non-disposing boundary actually needed? Nothing is being built for this yet.
